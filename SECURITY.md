# Security

## What this plugin promises

With the daemon reached over the relay or Tailscale, and an honest but careless agent:

- **On its way, a value is sealed.** What you type, and a file you pick, drop or paste, leaves the app only as ciphertext: sealed to a one-time key of that request (X25519, HKDF-SHA256, ChaCha20-Poly1305), and bound to the request's id and to a digest of the keys it declared and whether each is optional. A file is sealed like text: its bytes travel as base64url inside the same sealed payload, so no RPC carries them in the clear, and the plugin keeps them nowhere but in their set in `drop/`. If sealing is impossible, nothing is sent: there is no plaintext fallback.
- **On the daemon, a value is a short-lived file.** On disk it exists in the clear only as a file of mode `0600` in a directory of mode `0700`, `<data>/drop/si-secret-<requestId>/<KEY>`, for at most 15 minutes after the write while the machine is awake, and within a minute of waking when it slept through that deadline. It goes earlier when the agent releases it, at the end of the turn its delivery message starts, and at every start and stop of the plugin. What a crash does to this is below.
- **Nowhere else.** No tool result, message to the agent, pill, status, RPC answer, log line, error, `requests.json` or `outbox.json` holds the value. The agent is given paths; no tool and no RPC returns a value.
- **The daemon names who asks.** A request belongs to the agent the daemon hands the plugin with the tool call, which the daemon names from the agent's connection to its MCP server. Nothing the call itself says (an argument, the agent's environment, a marker) is read. That keeps agents apart that use the connection Paseo gave them: none of them can put a request in another agent's chat. Of the four tools, status, cancel and release answer any other such agent, its parent included, as if the request did not exist. It does not hold against a process that calls the daemon as another agent: on Paseo 0.14.0-beta.1 the name a connection claims is not bound to a credential (below).

That is the whole promise. While a file of a set exists, any process of your OS user can read it, the agent included. What keeps the value out of the model is the agent's discipline (the skill: never read a `si-secret-` path) and the plugin showing the value nowhere: discipline, not a lock.

## When it does not hold

Each row is a condition and what follows from it. None is softened. The plugin flags one thing: a second, different submission to a request whose values were delivered is refused, marked on the pill and reported to the agent. Beyond that it neither prevents nor, in general, detects what a process that runs as you does.

### What the plugin cannot control

| Condition | What happens |
|---|---|
| The agent reads a file of the set | The value enters its context. The skill forbids it and the delivery message repeats it: a rule, not a lock. A rule in the agent's harness that refuses its file-reading tools on `si-secret-` paths adds a lock where that harness can enforce one |
| The agent feeds the value to a command that prints it | The value reaches the model through that command's output: a tool that echoes what it stored, a verbose flag, `set -x`, an argument repeated in an error. The skill lists moves that print nothing; which commands print is outside the plugin |
| Another process of your user reads the file while it exists | Nothing stops it. The modes `0600` and `0700` keep out other users only, and every agent of yours runs as you |
| The file system copies on write, or a snapshot or a backup runs while the file exists | Deletion is `unlink` and `rmdir`, and the content is not overwritten first: on a copy-on-write file system (APFS, Btrfs, ZFS) overwriting guarantees nothing. The blocks stay on the disk until they are reused, and a snapshot or a backup taken while the file existed keeps it |
| A value is held in memory | Byte buffers are wiped, in the app and on the daemon, but the strings made from them cannot be. The text you type is a string in the form for as long as it is open, and on the daemon the opened payload's values are strings until the garbage collector reuses their memory. Whoever can read that memory can read them |
| You paste into a file row, or pick or drop a file | The plugin reads no clipboard and moves no file. What you copied stays in your clipboard and in any clipboard history, and the file you picked or dropped stays where it was. While the paste area is open, what you pasted is on the screen |
| The value reaches its destination | Where the agent puts it (an `.env`, a secret store, a server) is outside the plugin. Whether that place is ignored by git, backed up or readable by others is for the agent and for you to check |
| You answer a truthful but harmful request | Inherent to the feature: the form shows the keys, and the agent's own message says why it asks |

### A hostile process that runs as you

An agent with a shell runs as your OS user, controls its workspace, and can read and write the plugin's data directory. Nothing here prevents what such a process does.

| Condition | What happens |
|---|---|
| A process calls the daemon's MCP endpoint for agents as another agent | On Paseo 0.14.0-beta.1 the daemon takes the calling agent's id from what the connection to that endpoint claims (`callerAgentId`), and lets the connection in with the one token it puts in the configuration of every agent it starts, with the daemon's password as the bearer token, or with nothing at all when the daemon has no password. So a process that can reach the endpoint (one of your user, which can read that token; one that knows the daemon's password; and any process at all on a daemon with no password) can call the plugin's tools as any agent whose id it knows: put a request, and its pill, in that agent's chat, a card that asks you for a secret on behalf of an agent that never asked (phishing), and look at, cancel or release that agent's requests. The plugin cannot tell such a call from the agent's own; the host is where it can be closed |
| Any owner session of the daemon calls the plugin's RPCs, an agent holding the daemon's local credential included | A handler is not told who is calling, so no call proves that a human acted. Such a caller can read a request's view (its keys, labels and public key, never a value), submit its own values before you do, decline a request, or send three submissions that cannot be opened and so close it (`retry_limit`). If it submits first, the files hold its values. Your own submission is then refused, the pill turns red, «Підозріле подання», and the agent is told to have you check what it did with the values and to rotate the secret. That flag is all the detection there is |
| A caller of `secure-input.drop.clear` | It deletes every set at once, as «Видалити всі файли секретів зараз» does. Agents lose the files they had not moved yet, and an agent whose delivery message was still waiting is told that the user deleted them. A denial, never a leak: the call answers two counts, and no path, name or value |
| A process plants `requests.json` or `outbox.json` | Both are read as hostile input: capped, never through a link, and entry by entry against a strict schema in which no field can hold a value. A planted outbox entry can at most make the plugin send a fixed message of its own again, to the agent whose request it is about, once per restart. A planted record that passes the schema is loaded. If it claims to wait or to be delivered, the next start ends it (`expired`, or `released` by `restart`) and puts a pill with the record's key names in the chat of the agent the record names; for one that claimed to wait, it also sends that agent the fixed message for a request the restart ended. A planted record that is already closed is announced by nothing on its own; with a planted outbox entry for it, the plugin sends that record's fixed message to the agent it names. No value can ride along, and nothing can be opened or written for such a record: the key to open it never existed in this run |
| A process plants entries or links in `drop/` | The start's sweep removes everything in `drop/`. A link is unlinked as a link and never followed, and removal goes at most 8 levels deep; what is deeper was not made by the plugin, and is left and reported. A `drop/` that is itself a link, or not a directory of your user, fails the start-up; put in its place while the plugin runs, it is refused by every write and every removal, nothing behind it is touched, and what was to go stays reported until it can go. Anything planted at a set's path but an empty directory makes that write fail (`write_failed`); an empty directory there is replaced by the set |
| A process swaps a directory for a link in the instant before a removal | Node has no `unlinkat` or `openat`, so every removal goes by path. Before each entry the plugin looks at the entry's directory again, and goes on only if it is still the directory it read (the same device and inode); `drop/` itself is held to this as well, and has to be a directory of your user, never a link. A swap that lands between that look and what it guards is not caught: for a file, its `unlink`, which then removes a file of the same name wherever the link leads; for a directory, its own first look, after which its removal goes on there, at most 8 levels deep. A write holds `drop/` when it begins and looks at it once more right before the rename that puts the set in place; between the two its files go by path into the directory it staged them in, so a `drop/` swapped for a link in that time leads those files to the same names where the link points. A process that can win these races can read or delete what they reach by itself |
| The data directory is inside a workspace (`PASEO_HOME` there) | The sets are files in that workspace while they exist, and a `git add -A` there can stage one. The plugin does not check where its data directory lies |
| `bin/`, where v1 was installed | It holds what agents created under v1 run: the stub and the shim that starts it. A process of your user can replace them between two starts, as it can change the plugin's own code. Each start writes the stub again, and under Node the shim too; under Electron the shim stays as v1 wrote it |

### Crashes, stops and restarts

| Condition | What happens |
|---|---|
| The plugin or the daemon is killed, or the machine loses power, while a set exists | The set stays in `drop/` until the plugin next starts: while it does not run, nothing deletes the set, not even 15 minutes after the write. The first thing a start does, once it has made sure the data directory is its own, is to sweep `drop/`, before anything else that can fail; a start that fails after that has still swept. What that sweep cannot remove is reported, and each such entry is tried again once a minute, by itself, until it goes; the sweep is not repeated, since it would take the sets delivered since. A plugin that never starts again leaves the set where it is |
| The plugin is stopped | Paseo 0.14 gives a stopping plugin 2 seconds before it sends SIGTERM. Within them the plugin wipes the keys of the requests that wait, releases every set as `stop`, saves, and sweeps `drop/`: the releases and the save get at most 1 second, and the sweep after them at most 500 milliseconds, whatever the work queue is still doing, so `drop/` is emptied even when a task in that queue is stuck. What the sweep cannot remove in that time stays for the next start. A record whose release the stop could not save reads `restart` at the next start, and an agent's waiting message then says the files went when the plugin restarted |
| The stop comes while the start-up hangs (a disk that stalls) | The stop waits up to 5 seconds for the start-up, longer than the 2 seconds Paseo gives the stop, and then goes on without it. Such a start-up has delivered no set, since every tool call waits for the start-up, so what can be cut short is only the sweep of what an earlier run left, which the next start makes. A start-up that comes back later begins no further step, and the step it was in asks, right before each thing it would still do in `drop/` or `bin/`, whether its plugin is still wanted |
| A write fails, and its clean-up cannot remove what it staged | The request is rejected (`write_failed`), and the half-written set stays in `drop/` under its temporary name, `si-secret-<requestId>.<random>.tmp`. The plugin keeps its name: «Секрети на сервері» turns red, and it is tried again once a minute, by itself, until it goes. The plugin's stop, its next start and «Видалити всі файли секретів зараз» take it too. Nobody is given its path |
| A set cannot be removed when its time comes | The request stays `delivered`, it is tried again once a minute, and «Секрети на сервері» turns red. «Видалити всі файли секретів зараз» tries again; so does deleting `drop/` by hand |
| A disk that stalls holds up the plugin's work queue | Every deletion but the stop's sweep waits in that queue, the deadline's included, so for as long as the disk stalls a set can outlive its deadline. The stop's sweep does not wait for the queue (above). A tool call waits there for its turn for at most 10 seconds and is then refused, `the plugin is busy; retry in a few seconds`, and what it asked for is not done later; neither is what a call that was canceled while it waited asked for. An operation that has begun is waited for to the end |
| The plugin restarts while a request waits for you | The request becomes `expired`, because the key to open it lived in memory only. The agent is told that the restart ended it, which is not the message for a request nobody answered in time |
| The plugin restarts while a set exists | The start's sweep removes it, and the request reads `released` (`restart`). A delivery message that still waits becomes the message that the files went when the plugin restarted; one already sent is not sent again. A set the sweep cannot remove keeps its request `delivered`, and «Секрети на сервері» red: the set is tried again once a minute, and the request reads `released` (`restart`) once the set is gone. Until then the request is like any delivered one, and a delivery message that goes out meanwhile gives the paths of the files that are still there. For as long as `requests.json` cannot be saved after a start, the file still shows the requests that waited as waiting, and every further start ends them and announces them again |
| A message to the agent is late or lost | A message for a busy agent waits, up to a day, in `outbox.json`. It is sent only after the daemon has answered that the agent is idle: when the agent's turn ends, or within about a minute of the agent becoming idle some other way (the plugin asks once a minute). A check that fails or is not answered is not taken for "idle", and the message stays. Agents that have a message waiting are asked one after another, those that did not answer last time after the others; a call to the daemon for one of them may take 30 seconds, or what is left of the 45 seconds one round may take, and 1 second once those are used up. The plugin checks that the agent is idle and then sends, so a turn that starts in between can be interrupted; rare. A message is sent once and is lost only in these cases: the plugin dies before the message was saved; it dies or is stopped after the message was taken out of `outbox.json` and before the send finished; the one send fails or is not answered in time (it is never tried twice); the message waited longer than a day, or more than 256 messages wait and it is the oldest, or the clock was set back by more than a minute while it waited; the agent is archived; the plugin no longer has the request the message is about, because `requests.json` could not be read at a start or the request left the history of the last 200 closed ones first; the change of state was still being saved when a stop of the plugin ran out of its time; or `outbox.json` was replaced by something the plugin did not write. A message about delivered files is not sent at all when the agent released those files before it went out. The agent may then need a nudge from you |
| The plugin is stopped while messages or pills wait | No further pill is put on a timeline, and no agent is asked whether it is idle. One send can still start: that of a message that was being taken out of `outbox.json` at that very moment. A message that was not sent stays in `outbox.json` for the next start. A change of state whose save was still under way when the stop ran out of its time is saved and announced by nobody, by this start or the next: no message for it, and the pill goes on showing the state before it. In each of these cases the form behind the pill shows the true state |
| A pill cannot be put on the agent's timeline | The pill is the only way to the form, so it is tried again once a minute and whenever the daemon next calls the plugin, until it lands, and only once in five minutes while the daemon has left three appends of it unanswered. Until then nobody can answer the request. An older state that lands late is followed by the latest one |
| The plugin is removed, or never starts again | What the next start would have swept stays in `drop/`: the sets of a run that was killed, and what a failed write left. Nothing else of the plugin's holds a value |

### The channel and the versions

| Condition | What happens |
|---|---|
| A direct LAN connection with a password | The WebSocket is not encrypted. An active attacker can swap the request's key and read what you type. Enter secrets over the relay or Tailscale only |
| Someone sees the size of what you send | The sealed payload is padded to a multiple of 1 KiB, so its size tells how much you sent, rounded up to that multiple, and not how long any one value is |
| The app is older than the plugin requires (0.14.0-beta.1) | The plugin runs on the daemon, but the pill, the form and the settings screen do not load, so that device cannot answer requests. `paseo plugin ls` does not show it. The daemon must be at that version or later too |
| The reply to your submission is lost, and you press → again with other values | The form first reads the request again, and sends nothing if the request has been answered. That narrows the window and does not close it: a first submission still waiting in the plugin can win after that reading, and your second one is then refused and flagged as a second, different submission, though both were yours. With unchanged values the form sends the same sealed data again, which is never flagged |
| Linux | Developed and run on macOS. Linux is declared supported, and the test suite passes on it (Node 22, as a user that is not root); the plugin has not been run on a Linux daemon |

## Why approval is not a button

A Paseo plugin's RPC handlers are not told who is calling, and any process that can open an owner session of the daemon can call them. A plain "approve" RPC would prove nothing: an agent could press it. In this design the act of typing a value nobody else has is the approval, and no RPC returns a typed value.

## Reporting

Report a vulnerability privately, through GitHub's private vulnerability reporting on [dutchakdev/paseo-plugin-secure-input](https://github.com/dutchakdev/paseo-plugin-secure-input): the **Security** tab, then **Report a vulnerability**. Do not open a public issue for it, and do not include real secrets in a report: use test values, and leave out the content of any `si-secret-` file.
